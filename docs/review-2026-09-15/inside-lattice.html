Inside Lattice

Lattice is the person's own record of facts about themselves, kept on their phone, encrypted with a key Salt never holds. Agents ask for facts through Salt one granted request at a time, and the phone decides what leaves. This page shows how it is built, what that buys, and where a normal database would have been the better tool.

Where it lives

Three parties, one of which can read.

Lattice runs inside the Salt web app on the phone: a Rust core compiled to WebAssembly, run in a Web Worker, writing encrypted files to the browser's Origin Private File System. The core only ever sees plaintext records; the worker owns every key and does every encryption with WebCrypto. The root key is generated on the device, imported as a non-extractable key, and is never derived from a password.

The Salt server sees two things: the shape of each grant (which selectors, auto or ask, when standing access expires) and an opaque backup blob. Requests, releases and facts ride inside end-to-end encrypted chat messages, so the server relays them without being able to read them.

The one documented touchpoint with the rest of Salt is backup: the wallet vault's messages key wraps Lattice's raw root key once, and the wrapped key travels with the encrypted export to the server's backup row. After a vault recovery on a new phone, that wrap opens, the root key comes back, and the Lattice is restored. The worker itself imports nothing from the vault.

The data

A typed tree with typed links, in a closed schema, sorted into compartments.

Every fact is a node of a schema type. The type's first segment names its compartment, and a compartment is the unit of both encryption and access: one file, one derived key, one line in a grant. Seven hold facts about the person. The eighth, system, holds grants, the disclosure log and destroy markers, and a grant can never name it.

The schema is closed and versioned inside the crate. An agent cannot register a type, and a proposal with an unknown type or field is dropped silently. There is deliberately no type in which a private key, seed phrase, password, account number or card could land, and a test scans the schema for those words. Text values are capped at 2,000 characters and a node at 32 fields, so a trusted-write agent cannot turn a field into an unbounded channel.

Reads are path queries (preferences/food/*, preferences/food/cuisine/Japanese) with field filters, a traverse of up to four hops along chosen link types, and an on-device full-text search over each node's name and note.

A request, end to end

Grant, request, evaluate, consent, release, log. Deny by default.

Before anything, the person creates a grant for an agent on the Agent access page: a list of selectors, each marked auto (release without asking) or ask (show me first), optionally a compartment the agent may write into directly, and optionally standing access for 90 days. The server stores that shape and binds it to the agent's current key fingerprint. The phone mirrors it into its own system compartment and evaluates locally.

The wire format is two lines: a marker, then JSON. The agent only ever sees paths and values, never node ids, and never who wrote a fact beyond you or agent.

[[SALT-LATTICE-REQUEST id=01J8XK3V9Q4R5S6T7U8V9W0XYZ]]
{"purpose":"pick a restaurant for Friday","asks":["preferences.food.cuisine.*","preferences.food.restriction.*"]}

[[SALT-LATTICE-RELEASE id=01J8XK3V9Q4R5S6T7U8V9W0XYZ]]
{"request_id":"01J8XK…","facts":[{"path":"preferences/food/cuisine/Japanese","type":"preferences.food.cuisine",
  "field":"strength","value":0.8,"author":"you","updated":1789580100000}]}

Two more message kinds share the rail. A standing push is a release the phone sends on its own after a local change, for grants with standing access: auto fields only, only what changed since the last acknowledged sequence number, only until the 90-day expiry. A proposal is an agent writing a fact in; it lands pending for the person to accept or reject on the Your data page.

Writes, versions, backup

Log-structured on disk, flushed before every reply.

The core is a log. A record carries a global sequence number, a timestamp, its compartment and a body. Writes accumulate per compartment; after every mutating call the worker takes the pending plaintext, encrypts it as one frame with that compartment's key, appends it to the compartment's file, and only then answers. A caller's await means "on disk". If the encrypt or append fails, the worker hands the same bytes back to the core and the flush is retried rather than lost.

  • Open decrypts each compartment's frames, loads them, sorts by sequence and builds the index. Five thousand nodes open in 30 ms on Chromium and 42 ms on WebKit, wasm-only; 43 and 53 ms including file reads and decryption.
  • Destroying a compartment deletes its file and writes a marker in system. Later writes to it are refused, and a restored copy of the file refuses to load.
  • Compaction rewrites a compartment as current versions plus the version list. It exists and is not run automatically yet.
  • Backup is the encrypted files concatenated with a manifest, uploaded to one server row with a version compare-and-swap. Restoring the root key on a new device is wired; restoring the data blob is not yet, and when it is, a counter inside the encrypted manifest must refuse older blobs so the server cannot revive a destroyed compartment.

What we get

Each guarantee is a named rule with a test that failed before the code existed.

  • Salt cannot read a factdesignThe plaintext exists only in the worker on the phone. The server relays ciphertext and holds grant shapes and an encrypted backup.
  • Closed schemaR1 · R14Agents cannot add types. No type exists for a key, phrase, password, account or card, and a test keeps it that way.
  • Deny by defaultR5No grant, a revoked grant, a rotated key and no matching data all produce a byte-identical release. Omission is indistinguishable from absence.
  • Nothing sent without being shownR9An ask item is never in the auto set; approving a subset releases exactly that subset.
  • Authorisation decided in the coreround 2Release re-evaluates the grant and drops anything no longer allowed, whatever the calling JavaScript passes in.
  • Every release is loggedR12One disclosure entry per release, on the phone, listing agent, purpose and the fields that went out.
  • Authorship is maskedR7An agent learns a fact was written by you or by an agent, never which one.
  • Every write is a versionR2Edits, status changes and deletes are all kept versions; nothing is overwritten.
  • Agent writes wait for youR3 · R4A proposal lands pending unless the grant trusts that compartment, and pending facts are never released.
  • Group chats never answerR6The phone redirects to a private lane with that agent before evaluating anything.
  • Standing access expiresR13Opt-in per grant, auto fields only, changes since the last acknowledged sequence, 90 days, renewable.
  • Narrow rules winB2 · S4A rule on a nested type overrides a broader one, and a tie between ask and auto resolves to ask.

Versus a relational database

The honest comparison is about who can read, not about speed.

The question has three answers depending on what "a relational database" means: Postgres on the Salt server, SQLite compiled to wasm on the phone, or the relational model in the abstract. The diagram draws the first, because it is the one that changes what Salt can promise.

Is it beneficial over a relational database? For the job it exists to do, yes, and not on a dimension a database competes on. Salt's claim is that it cannot read a person's facts. A server-side database cannot make that claim at all, however good its policies; the operator can always look. Lattice moves the plaintext and the decision onto the person's device, which turns "we won't" into "we can't". That is the product, and it is why the grant engine, the masked release, the byte-identical denial and the on-device log are in the core rather than in application code around a general store.

Where a relational database is better is everything else: ad hoc questions across many people, large volumes, several devices writing at once, reporting, and forty years of tools. None of those are Lattice's job. Salt's own relational database keeps doing its work, including holding the grant rows and the backup row that make Lattice recoverable.

The fair on-device alternative would have been SQLite in wasm. It would give SQL and a familiar model, at several times the download, and every guarantee in the "What we get" list would still have to be written on top of it. Lattice's small surface is the trade: fewer query shapes, in exchange for a policy engine that is tested as rules rather than assembled per feature.
