Lattice, Signed

A redesign of Lattice around signed claims. The store stays on the person's device and Salt still cannot read a fact. What changes is what leaves the phone: not a value in a chat message, but a signed, audience-bound, expiring claim that any counterparty can verify against a key Salt registered. That is what makes the person's authority into Salt's authority, and it is one change that resolves most of what the adversarial review found.

Thesis

Salt is the authority for identity, standing and consequences. It registers keys, knows who is verified, who paid whom, who delivered, and it runs the rails where money and work orders settle. It signs that.

The person is the authority for facts about themselves. The facts live on their device under their own key. When an agent needs one, the device issues a claim and signs it. Salt never sees the fact.

Agents execute against claims, not against chat. A claim names its audience, carries its grant, expires, and verifies offline against the subject's key, which Salt vouches for. It can travel to another agent, a merchant or Grains and still be checked. It cannot be laundered, duplicated or spoofed, and it is valid while the person sleeps.

Everything below is the mechanism for those three sentences. The current branch keeps its crate, worker, compartments, rules and grants; it replaces the release format, adds a signing key, adds predicates and tiers, and moves the log to server-sequenced frames.

Three signers, one curve

Every signed document uses the primitives Grains already specifies, so nothing new has to be verified by anyone.

  • Saltauthority key · secp256k1 in KMS · did:key:zQ3s…Signs attestations: this DID belongs to this Salt account, created then, verified contacts, standing as the person allows. Countersigns grants as registrar. Never signs a fact.
  • The personclaim key · secp256k1 · generated on device · wrapped in the vaultSigns claims, consents, receipts and grants. The public half is registered on the account like the PGP fingerprint is today, and bound to the PGP key by a signed binding so the two custodies name one person.
  • The agentagent key · secp256k1 · did:key · Grains-nativeSigns requests, so the phone no longer asks the server who sent one. Is the audience of claims and grants. Presents claims onward with its own signature over the presentation.

Primitives, inherited verbatim from grains-identity/0.1: secp256k1 keys encoded as did:key, canonical JSON (sorted keys, no whitespace, no floats, sig removed), ES256K with RFC 6979 nonces and low-s, signatures as {alg, kid, value}. A verifier that already checks a Grains receipt checks a Salt claim with the same code.

The documents

Five signed shapes. Specs live in the Grains repo beside the credential-authority spec, vendor-neutral, with Salt as the reference registrar and the reference issuer, and vectors mirrored into salt-api tests, the way credential-authority/0.1 already works.

1. Claim personal-claim/0.1

What leaves the phone. One claim per fact field or per predicate. Self-contained: it embeds the attestation, so a verifier needs nothing outside it.

{
  "spec": "personal-claim/0.1",
  "id": "018f5a2c-…",                       // UUIDv7, sortable
  "subject": "did:key:zQ3sPerson…",          // the person's claim key
  "audience": ["did:key:zQ3sAgent…"],        // who may hold and present this
  "grant": "g_01J8W…",                       // the grant it was issued under
  "kind": "value",                           // value | predicate
  "path": "preferences/food/restriction/Peanuts",
  "type": "preferences.food.restriction",
  "field": "kind",
  "value": "allergy",
  "tier": "contacts",                        // public | contacts | private
  "purpose": "pick a restaurant for Friday", // the request's purpose, capped at 280
  "issued_at": "2026-09-15T14:02:11Z",
  "expires_at": "2026-09-22T14:02:11Z",
  "receipt": "r_018f5a2c-…",
  "attestation": { …salt-attestation/0.1, signed by Salt… },
  "sig": {"alg": "ES256K", "kid": "did:key:zQ3sPerson…", "value": "…"}
}

A predicate claim carries a question and a signed answer instead of a value. The fact never leaves.

{
  "spec": "personal-claim/0.1",
  "kind": "predicate",
  "predicate": {"op": "none", "path": "preferences/food/restriction/*", "field": "kind", "arg": "allergy"},
  "answer": false,                           // "no allergy restrictions": true/false only
  "tier": "contacts",
  …subject, audience, grant, issued_at, expires_at, receipt, attestation, sig…
}

Predicate operators are a closed vocabulary evaluated inside the crate: exists, none, eq, in, gte, lte, before, after, free_between (schedule). No free-form expressions, no composition beyond one operator per claim, and each predicate is governed by the same selector rules and tier ceiling as the value it asks about.

2. Grant salt-grant/0.1

Today a server row. Now a document the person signs and Salt countersigns, stored on the server as before, mirrored into the store as before, and presentable by the agent as proof it may hold claims from this subject.

{
  "spec": "salt-grant/0.1",
  "id": "g_01J8W…",
  "subject": "did:key:zQ3sPerson…",
  "audience": "did:key:zQ3sAgent…",
  "rules": [{"selector": "preferences.food.*", "mode": "auto"},
            {"selector": "schedule.*",         "mode": "ask"}],
  "ceiling": "contacts",                      // highest tier any rule may reach
  "predicates": true,                         // may ask predicates under these rules
  "trusted_writes": [],
  "standing": {"expires_at": "2026-12-14T00:00:00Z"},
  "version": 3,
  "issued_at": "…",
  "sigs": [{"alg": "ES256K", "kid": "did:key:zQ3sPerson…", "value": "…"},
           {"alg": "ES256K", "kid": "did:key:zQ3sSalt…",   "value": "…", "role": "registrar"}]
}

3. Request signed

The same marker and body as today, plus a signature by the agent's key. The phone verifies the signature before evaluating anything. The server-supplied fingerprint lookup is gone; agent identity is the key that signed the request, and the grant's audience is that key.

[[SALT-LATTICE-REQUEST id=01J8XK3V…]]
{"purpose": "pick a restaurant for Friday",
 "asks": ["preferences.food.cuisine.*", "preferences.food.restriction.*"],
 "predicates": [{"op": "free_between", "path": "schedule/*", "arg": ["2026-09-18T18:00Z", "2026-09-18T22:00Z"]}],
 "wants": "claims",
 "sig": {"alg": "ES256K", "kid": "did:key:zQ3sAgent…", "value": "…"}}

4. Receipt salt-receipt/0.1 · type disclosure

Signed by the person. Lists the claim ids issued, to whom, under which grant, when. Kept in the disclosure log on the device and handed to the agent with the claims, so an agent can prove to a counterparty, or to Grains' receipt chain, that it obtained what it holds legitimately. A consent receipt records the person's approval of ask items; a revocation receipt tells an agent to drop what it holds.

5. Attestation salt-attestation/0.1

Signed by Salt's authority key. Short-lived (24 hours), fetched by the phone and embedded in each claim. It says only what a public profile already says, plus what the person opts in to.

{
  "spec": "salt-attestation/0.1",
  "subject": "did:key:zQ3sPerson…",
  "pgp_fingerprint": "A1B2…",                 // the binding between the two custodies
  "account": {"username": "ada", "created_at": "2025-11-02", "legal_accepted": true},
  "standing": {"verified_contacts": 12, "real_money_counterparties": 4, "hiring": "…"},  // person-chosen fields
  "issued_at": "…", "expires_at": "…",
  "sig": {"alg": "ES256K", "kid": "did:key:zQ3sSalt…", "value": "…"}
}

This is the sentence "the user's authority, and thus Salt's authority" as bytes: the claim is the person's signature, the attestation inside it is Salt's, and the DID in both is the same.

A request, signed

The same six steps as today. Three of them change.

Predicates and tiers

Two additions to the store that make the identity problem tractable.

Tiers on facts, a ceiling on grants

Every node carries a tier: public, contacts, private, never. It defaults from the compartment and from where the fact was learned: a fact captured from a room with a verified contact defaults to contacts, one from a lane with someone marked partner to private. Every grant carries a ceiling, defaulting to public for an agent the person has never dealt with. evaluate applies the ceiling beside the selector match, in the crate, so the rule has a test. never facts are never in a claim of any kind, and their absence is byte-identical to any other absence.

Sensitive compartments

New compartments intimacy, belief (religion, politics), status (immigration, legal), mind (mental health): ask-only, never standing, never auto, never predicates, and excluded from the compartment-level checkbox so a wide grant cannot include them by accident. Free text on any node takes the strictest tier of its compartment, because a note is where anything without a type ends up.

Predicates: the answer without the fact

"Is vegetarian", "free Friday evening", "budget covers this", "no allergy restrictions". The crate evaluates the operator over accepted nodes under the same rules and ceiling as a value, signs the boolean, and the fact stays on the phone. For a stranger's agent most tasks need only predicates, so the default grant for a new agent is predicates only, ceiling public, and values are something the person adds deliberately.

Predicates leak bits by repetition, so they are budgeted: a per-grant daily count enforced at issue time from the receipt log, refused past the budget with the empty release. And the budget refusal is not distinguishable from "nothing matched".

Availability without the phone

An authority that is offline when the person sleeps is not one agents can build on.

  • Claims outlive the session. An on-demand claim is valid for seven days by default, a standing claim until the grant's standing expiry, at most ninety days. The agent holds them. A task at 3 a.m. runs on claims issued at 6 p.m.
  • Standing is re-issuance, not a firehose. For auto selectors under a standing grant, the phone issues a claim bundle at grant time and re-issues when a covered fact changes, on any open device, after pulling the shared checkpoint. What travels is a claim per changed field, not a diff of values.
  • Revocation is a signed receipt the agent must honour, delivered in chat; the SDK drops matching claims on receipt and Salt's grant row is the second source of truth for a verifier that checks online.
  • Requests while every device is closed are answered when one opens, from a buffer keyed by message id, and the agent's SDK keeps the request pending rather than timing out into "you'll hear back", which today it cannot deliver on.

The store

Kept: the crate, the closed schema, compartments, versions, rules R1–R14. Changed: where the log lives and how records are identified.

  • Server-sequenced frames. Encrypted frames go to lattice_frames; the server assigns a per-user monotonic seq and broadcasts a content-free cable event; every device pulls since its last seq; the device's files are a cache. Records carry ULIDs; order is the server seq. Two devices editing one node produce two kept versions and the server's order says which is current. The backup row keeps only the key wrap. A new device unwraps the root and claim keys with the messages key and pulls.
  • Per-compartment random keys wrapped by the derived key, so destroy deletes the wrap and an old frame is unrecoverable.
  • Frame integrity. The per-compartment frame index is in the AAD and a high-water mark per device is kept in IndexedDB, so a deleted or withheld frame is detected on any device that has seen past it.
  • Compaction bound on the wasm class; a device uploads a snapshot frame and the server drops earlier frames for that compartment.
  • Dedup and identity. An agent's or Ion's proposal looks up an existing node by type, name and parent and edits it; identity.person is a singleton; delete cascades to children. A claim carries the node's path and the receipt carries the node id, so a later proposal can name what it supersedes.
  • Trusted writes stay, but a trusted-write node is ineligible for any claim to an audience other than the writer until the person has reviewed it once, and every node shows its author.

The binding between a Salt username and a claim DID is the one place Salt is trusted for identity. It is the same trust as today's PGP fingerprint, and the same remedy applies: verified contacts compare DIDs in person (the existing fingerprint verification flow extends to the claim DID), devices pin the DIDs of contacts they have seen, and a key change surfaces the way a PGP key change does now.

Ion's place

The bastion has to be full and current without a third party reading the chats.

  • First, the person. "Add to your data" on the Your data page, driven by the schema. Item one of the fix plan; it does not depend on anything here.
  • Second, capture at the moment of answer. When an agent's request could not be met from the store and the person answers in the lane in prose, the reply gets one-tap chips for the types the request asked for ("Save as: food restriction · cuisine"). The answer is already typed; saving it is a tap. Provenance and tier come from the lane. This is the highest-precision extractor available and it needs no model.
  • Third, recall. The embedding index works today; it powers "Find in your data" and, later, Ion suggesting which existing node a proposal supersedes.
  • Fourth, extraction. Grammar-constrained decoding against the schema, then a LoRA, decided once the owner's own labelled conversations exist. Ion's proposals land pending, carry the lane's tier, and dedup against existing nodes. Unchanged from the recorded decision, just no longer the thing the product waits on.

Build plan

Four phases. Each ships on its own and each is worth having without the next. The fix-list numbers refer to "Lattice Under Attack".

Phase 0 · Stop the bleeding

days · fix plan 1–8 · no new concepts

  • Standing release path in the crate, readiness buffer for requests, sequential grant sync, close flushes, quoted purpose, padded releases, author on nodes, "Add to your data".

Phase 1 · Keys and specs

about a week · API + Grains spec + vault

  • Salt authority key in KMS (secp256k1, sign-only, the Grains hosted-agent pattern); its DID at GET /api/.well-known/credential-authority under a new claims section.
  • Claim key per person: generated on device, wrapped under the messages DEK beside the PGP key, registered on the account; a signed PGP↔DID binding; enrolment on next sign-in for existing accounts.
  • Agent DID on registration; PATCH /api/v1/agents/did for self-service, like the callback route.
  • Specs and vectors in the Grains repo: personal-claim/0.1, salt-grant/0.1, salt-receipt/0.1, salt-attestation/0.1; grains verify accepts a claim; vectors mirrored into salt-api tests.
  • Attestation endpoint, 24-hour documents, person-chosen standing fields.

Phase 2 · Signed protocol

about two weeks · crate + worker + SDK + web

  • Crate: claim builder (canonical JSON minus sig), tier and ceiling in evaluate, predicate operators, sensitive compartments, receipt records.
  • Worker: vendored noble-secp256k1, sign claims and receipts, verify request signatures, claim key in memory while open.
  • SDK: agent key, signed requests, verifyClaim, claim cache with expiry, receipts, revocation, dedup; salt-claude-agent hands claims to the model as data, never instructions.
  • Web: tier picker and ceiling on the Personal data card, predicates-only default for new agents, consent sheet shows predicates as questions, capture-at-answer chips.
  • Wire: claims in releases; grants countersigned on create and update.

Phase 3 · The store

about two weeks · API + crate + worker

  • lattice_frames, cable event, pull-since, claims mutex; ULID records and server-seq ordering; OPFS as cache.
  • Per-compartment random keys, frame index in the AAD with a device high-water mark, compaction by snapshot, tombstone list in the manifest.
  • Dedup on proposals, singleton person, cascade delete, per-agent log index, schema version stamps.
  • Honest perf fixture: thousands of single writes, wall time gated, on the iOS Simulator.

Decisions to take

Four calls the design makes that you may want to overrule. Each has a default and the reason for it.

secp256k1 (ES256K) or P-256 (ES256) for the claim key? Default: secp256k1, because Grains, every agent runtime and every EVM wallet already speak it, and a Grains verifier checks a Salt claim with no new code. Cost: WebCrypto has no secp256k1, so the private key is raw bytes in worker memory while the store is open, signed by a vendored pure-JS library. P-256 would let WebCrypto hold it non-extractable, at the price of a second curve for every verifier. The PGP key is already raw in memory when openpgp.js uses it, so the posture is not new.

A separate claim key or the PGP key? Default: separate. PGP signatures have no canonical JSON, no offline-verifiable compact form, and no place in Grains' receipt chain. The binding document ties the two so a contact who verified one has verified both.

Where do the specs live? Default: the Grains repo, vendor-neutral, with Salt as the reference registrar and issuer, exactly as credential-authority/0.1 is done today. The alternative, Salt-only specs, makes the claims Salt's format rather than a format Salt is the authority for, which is the weaker position for the vision.

Default grant for a stranger's agent: predicates only, ceiling public? Default: yes. Most tasks need answers, not values, and it makes the first grant safe by construction. A person who wants an agent to hold values adds rules deliberately, and the picker says what each one exposes.
