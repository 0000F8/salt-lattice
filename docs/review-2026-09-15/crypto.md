# Cryptography review

## Verdict (3 sentences, contrarian, honest)
The primitives (AES-256-GCM, HKDF-SHA256 from a real 32-byte CSPRNG root, non-extractable CryptoKeys, real `crypto.getRandomValues` in wasm) are all correctly chosen and correctly wired — this is not a "someone rolled their own crypto" report. But the frame format has no integrity story across frames or across time: any party who can touch the OPFS file or an old backup blob can silently delete, freeze, or resurrect data, and the crate's own "byte-identical release" privacy guarantee (R5) is destroyed the moment that payload leaves the crate and becomes an OpenPGP message, because nothing pads it. Destroy-a-compartment is not "destroy" in any cryptographic sense — it is "delete the pointer to a still-valid key" — and that fact quietly defeats several other guarantees documented elsewhere as settled.

## Findings

### F1. Destroying a compartment doesn't destroy its key, so any surviving backup blob un-destroys it
- Kind: premise-attack
- Severity: critical
- Evidence: `crypto.js:135-137` derives the compartment key as `HKDF(root, salt="lattice/v1", info=compartment)` — a **pure function** of two values that never change (`root`, the compartment's name). `lattice.worker.js:574-590` (`doDestroyCompartment`) deletes the on-disk file and writes a marker, but never touches `rootKey`. `CLAUDE.md` even says the quiet part out loud: "Per-compartment random keys (destroy the key instead) are the recorded phase 2 option" — i.e. it's known and deferred.
- Attack: person destroys `health` compartment. Six months later a backup blob taken *before* the destroy — sitting in `salt_backups` on the server, in a downloaded export, in a device's Time Machine snapshot, anywhere — gets fed into `importBackup` (`lattice.worker.js:615-644`). `writeWholeCompartmentFile` (`:237-248`) writes the old ciphertext straight back to disk with no destroyed-check at write time; the destroy marker that would normally shield it (`store.rs` load_frame's destroyed check, cited in `RISKS.md` A3) lives in the `system` compartment of the OLD blob, not this device's current state, so it doesn't help. On next `open()` the health data is back, byte-for-byte, and there is nothing in the crypto to say it shouldn't be — the key still works, because it was never revoked, only orphaned.
- Solution: give every compartment a random KEK generated at first write, wrapped by the HKDF-derived compartment key (so today's derivation becomes a key-*wrapping* key, not the data key itself). `destroy_compartment` deletes the wrap. Old ciphertext is then genuinely unrecoverable — not just file-deleted — even from a blob that predates the destroy. This is exactly the option `CLAUDE.md` already named; it stops being optional once backups are load-bearing (A3 says import "appears nowhere outside vendor" today, but bootstrapRoot already restores the root from a backup row unconditionally, so the blast radius is one `importBackup` call site away).
- Cost: M

### F2. No cross-frame or cross-session sequence binding — frame deletion and rollback are undetectable
- Kind: caveat
- Severity: high
- Evidence: `frameAad(compartment)` (`crypto.js:24-26`) is `"lattice/v1/" + compartment` — identical for every frame ever written to that file. AES-GCM authenticates each frame's own bytes and that AAD, and nothing else. Frame order/position is not part of the AAD, and the on-disk position isn't even trusted: `doOpen` (`lattice.worker.js:438-482`) decrypts every frame and then **re-sorts by the `seq` field inside the decrypted plaintext** (`store.rs:159-163`, `finish_open` sorts by `record.seq` and does `next_seq.max(record.seq+1)`). `seq` is described as "global and monotonic across every compartment" (`store.rs:15-16`) but nothing persists a device-side high-water-mark outside the frames themselves.
- Attack: an attacker (malicious extension with OPFS access, forensic image of the device, or a restored/edited backup blob) deletes one full, validly-authenticated frame from the middle or end of `finances.frames`. Each remaining frame still decrypts and authenticates fine — GCM has no idea a sibling frame existed. `decodeFramesTolerant` only guards a **trailing partial** frame (`crypto.js:91-108`, the S9 fix); a complete frame removed from anywhere is invisible. Because `seq` is store-global, a "gap" in observed seqs is not even anomalous — a legitimately-untouched compartment naturally has gaps where other compartments' seqs landed. There is no way, cryptographically or logically, for the device to notice a write is missing.
- Attack (reorder is actually a non-issue, note this explicitly): swapping two frames' byte ranges on disk is harmless because `finish_open` re-sorts by embedded `seq` regardless of on-disk order — so *reordering* is self-healing, but that same design choice is *why* deletion is undetectable (the file's order carries no authority, so nothing can be checked against it).
- Solution: bind a monotonically-increasing per-compartment frame counter into the AAD (`"lattice/v1/" + compartment + "/" + frame_index`), and persist the last-seen frame_index per compartment in IndexedDB (next to `rootKey`, non-exportable) independent of the file itself. On open, if the loaded file's max frame_index is lower than the persisted watermark, refuse to open that compartment and surface a tamper error instead of silently loading a smaller-than-expected history.
- Cost: M

### F3. Backup rollback defense ("a monotonic counter inside the manifest") doesn't cover the one scenario backups exist for
- Kind: premise-attack (disputes A3's accepted framing)
- Severity: high
- Evidence: `RISKS.md` A3 accepts the rollback gap and proposes: "a monotonic counter inside the encrypted manifest, refused below the highest the device has seen." `backup.js:87-121` (`bootstrapRoot`) shows the actual call pattern: restore-from-backup runs on **a device with no local root at all** — a fresh install or a lost/wiped phone (`has` is false at `:91`, backupRow exists at `:106-112`). "The highest the device has seen" is state that, by construction, does not exist on the one device this path is for.
- Attack: server (or anyone who can serve a chosen backup row — A1 already establishes the server is trusted for other bindings) hands a lost-phone recovery flow a stale-but-validly-signed-by-its-own-manifest blob. There is no local memory to compare against, so "refused below the highest the device has seen" refuses nothing. The device happily restores a rolled-back graph and believes it's current.
- Solution: the monotonic counter has to live somewhere the *attacker* doesn't control and the device *does* retain across a wipe — that's not really possible for phase-1 Lattice's threat model without a third store. The honest fix is smaller: make `exportBackup` embed, inside the encrypted manifest, the full list of `DestroyCompartment` markers seen so far (not just current compartment names/sizes), and make `importBackup` refuse silently if the *current* device (when one exists, i.e. every path except first-ever restore) has locally destroyed a compartment the incoming manifest still lists as live. That closes the "undo a destroy on an already-alive device" case, which is the actually-common one (F1's attack does not require a wiped phone). Accept, explicitly and in writing, that first-restore-onto-a-wiped-device has no rollback defense possible under this architecture — don't let the manifest-counter language imply it does.
- Cost: S (manifest tombstone list) to close the common case; the wiped-device case is accept-only.

### F4. R5's "byte-identical release" privacy property does not survive being sent
- Kind: premise-attack
- Severity: medium
- Evidence: `access.rs` (`release`, header comment) claims: "a no-match release follows [byte-identical] directly" from depending only on `request.id` and `facts`. That's true of the `ReleasePayload` struct. But `requestHandler.js:85-93` (`releaseAndSend`) takes that payload's `facts` array and does `buildRelease(randomId(), { request_id, facts: releasedFacts })` → `markers.js:61`: `` `[[SALT-LATTICE-RELEASE id=${id}]]\n${JSON.stringify(body)}` `` — a plain string whose length is directly proportional to how many facts got released. `sendToChat.js:20-21` encrypts that string with OpenPGP and posts it with no padding step anywhere in between.
- Attack: the Salt server (or anyone who can see ciphertext sizes on the wire/at rest — exactly the class of observer R5 exists to defend against) distinguishes "0 facts released" (a short ciphertext) from "12 facts released" (a long one) purely from message byte length, without decrypting anything. That reconstructs exactly the signal R5's "deny by default looks identical to deny for cause" property was designed to hide — the crate-level property is real but scoped to the wrong layer.
- Solution: pad the JSON body (e.g. to the next power-of-two or a fixed small set of size buckets, mirroring `padBlock` in `crypto.js:224-230`, which already solves this exact problem for the backup manifest) before it goes into `buildRelease`/`buildStandingRelease`. Cheap and there's already a working pattern to copy in the same repo.
- Cost: S

### F5. `agent_fingerprint` is both the authorization check and something the server can hand the client fresh on every call
- Kind: caveat (extends A1 rather than duplicating it)
- Severity: medium
- Evidence: `access.rs:107-109` (`grant_is_valid_for`) is the entire authorization gate: `grant.revoked.is_none() && grant.agent_fingerprint == request.agent_fingerprint`. `requestHandler.js:45-48/113-121` sources `request.agent_fingerprint` from `GET /api/v1/users/:username`, a live, uncached (`?_=${Date.now()}`) call to the Salt server, on every single incoming request marker.
- Attack: this is A1's "compromised server can bind any identity" risk, but worth stating the crypto-specific corollary precisely: the fingerprint check exists to detect *key rotation* (an agent's key changed since the grant was approved, PROTOCOL's stated purpose), but it cannot detect *server-supplied impersonation*, because the server is the sole source for both the claimed identity (`msg.user.id`/`username`) and the "proof" that the identity's key matches (the fingerprint fetched from that same server). The check has zero independent legs — it is not cross-referenced against, e.g., the actual OpenPGP key that encrypted-for-this-device the incoming message, which the client already possesses locally without asking the server anything.
- Solution: DESIGN's own stated stronger version — derive the fingerprint from the sender's key already visible in the chat payload — is the right fix and is cheap: `msg.user.public_key` (or the chat session's member list) is already fetched as part of ordinary chat sync, so this removes a network round-trip AND a trust dependency in the same change.
- Cost: S (the fix is already scoped in RISKS.md; escalate it from "recorded" to "do it," it's not expensive)

### F6. `deriveBlobKey`'s `purpose` string is caller-supplied and unvalidated
- Kind: bottleneck
- Severity: low
- Evidence: `crypto.js:140-142`, `lattice.worker.js:646-658` (`doEncryptBlob`/`doDecryptBlob`) take `purpose` as a bare string from the `call` args with no allowlist, and feed it straight into HKDF `info`. Compare to `LatticeGrant`'s selector validation (`lattice_grant.rb:93-165`), which is strict about every string it accepts.
- Attack: not currently exploitable (nonce is fresh-random per call, AAD matches purpose so cross-purpose ciphertext just fails to decrypt rather than leaking) — this is a latent footgun, not a live break. If a future caller ever reuses a `purpose` string across two logically-different secrets (e.g. two features both picking `"export"`), they'd silently share a key with no error until the AAD mismatch surfaces at decrypt time, which is a confusing failure mode to debug, not a confidentiality break.
- Solution: a small const allowlist (`"backup-manifest"`, whatever Ion registers) checked in the worker before deriving, same shape as `AAD` constants elsewhere in the codebase (e.g. `backupKey.js:17`).
- Cost: S

### F7. The root key sits in IndexedDB as a non-extractable CryptoKey with no gate — correctly scoped by A2, but the backup-key wrap doesn't rotate on vault password change
- Kind: caveat
- Severity: low
- Evidence: `backupKey.js:28-31` wraps the raw root under the vault's `messages` DEK. `CLAUDE.md`'s One Password section says a password change re-wraps vault DEKs under a new KEK (`ChangePasswordDialog.jsx`), but the *messages DEK itself* is what's being re-wrapped, not re-generated — so this is actually fine by construction (the DEK, and therefore the Lattice root's wrap under it, is stable across a password change; only the KEK protecting the DEK rotates). Flagging only because it's exactly the kind of assumption worth a one-line test asserting `wrapRootForBackup`'s ciphertext is unaffected by `ChangePasswordDialog`'s re-wrap path, since `backupKey.test.js` should already cover the encrypt/decrypt round trip but likely doesn't cover interaction with the password-change re-wrap flow specifically.
- Solution: add that one integration test; no code change indicated by this review.
- Cost: S

## The one thing I'd kill or change first
Ship per-compartment random KEKs (F1) before phase 2 touches production. Every other finding here (F2, F3) is a variant of "an old copy of the ciphertext can come back," and F1 is the one place where "come back" means "a person's own explicit destroy action is silently reversible forever." That is the single finding that turns a defensible accepted-risk list into a promise the product cannot actually keep once `PUT /api/v1/lattice/backup` starts writing rows in production, which — per `backup.js` — it already does at first Lattice use, well before `importBackup` is wired up client-side.

## What is actually good (max 3 bullets; be stingy)
- HKDF-Extract using a fixed public salt over a real 256-bit CSPRNG root (`doCreateRoot`, `lattice-wasm/src/lib.rs:36-46`'s `random_u64` genuinely goes through `crypto.getRandomValues`) is textbook-correct; the fixed salt is not a weakness here, and I'd have flagged it if it were.
- The `takeFrame`/`restoreFrame` flush-failure protocol (`lattice.worker.js:273-301`) correctly treats "encrypted but not yet durable" as a distinct state from "lost," which is the right instinct for a system where losing a write silently is worse than losing it loudly.
- `padBlock`/`unpadBlock` for the backup manifest (`crypto.js:214-249`) is a genuinely good, cheap size-hiding pattern — it's just not applied everywhere it needed to be (F4).
