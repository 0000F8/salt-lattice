# Security review

## Verdict (3 sentences, contrarian, honest)
The crate itself has already survived four internal review rounds and it shows: R5/R6/R7 hold up under direct code reading, and the fingerprint-rotation and destroyed-compartment checks are genuinely solid. But the JS glue that wires the crate to the wire protocol has at least one release-blocking bug (standing pushes silently deliver nothing while telling the disclosure log they succeeded) and one unresolved trust boundary the docs already admit but understate (the entire agent-identity chain — id, username, fingerprint — is server-asserted with zero cryptographic anchor, because Salt messages are encrypted but never signed). The consent sheet, the one place a person is asked to make a real access decision, renders agent-controlled free text as if it were Salt's own trusted copy — the exact anti-pattern CLAUDE.md already forbids for money UI.

## Findings

### F1. Standing pushes silently deliver zero facts and mark themselves successful
- Kind: bottleneck (crate/glue integration bug with security consequences)
- Severity: critical
- Evidence: `crates/lattice-core/src/access.rs` `release()` calls `evaluate(store, request)` fresh and keeps only facts that reappear in that fresh `auto`/`ask` set. `evaluate()`'s matching loop (`access.rs` in `evaluate`) is gated entirely on `request.asks` — if `ask_selectors` is empty, `!ask_selectors.iter().any(...)` is always true, so it `continue`s past every field and returns `{auto: [], ask: []}` no matter what the grant allows. `salt-fe/src/lattice/requestHandler.js:316-323` builds the `Request` for a standing push with `asks: []` (standing pushes drive off `standing_diff`'s grant-rule scan, not `asks`, by design). So every standing-push `release()` call gets `currently_allowed = []` and drops 100% of the real facts the worker's `standing_diff` computed. Confirmed by absence: `grep -rn "DisclosureKind::Standing" crates/lattice-core/tests/rules.rs` returns nothing — every `access::release` test uses `DisclosureKind::OnDemand`; the standing path was never exercised end-to-end.
- Attack: not an attacker-triggered exploit — a self-inflicted wound. A person turns on standing sharing for a grant (e.g. schedule → an agent that plans dinners). `pushStandingUpdate` (`requestHandler.js:311-326`) gets real facts from the worker, calls `release()`, gets back `payload.facts = []`, sends a `[[SALT-LATTICE-RELEASE ... standing=...]]` message with an empty `facts` array to the agent, and then calls `handle.ackStandingUpdate(grantId, seq)` (`requestHandler.js:326`) — which persists the checkpoint as if that diff had actually gone out. The window is never retried. The disclosure log (`DisclosureEntry.fields` is derived from the same filtered, empty `facts`) permanently shows `fields: []` for every standing entry. The person sees "standing sharing: on" and a disclosure log that looks like it's working; the agent gets nothing, ever.
- Solution: give `release()` a standing-aware path — either skip the fresh-`evaluate` re-check for `DisclosureKind::Standing` and instead re-run `standing_diff`'s own selector check against the passed facts, or have the JS glue call `standing_checkpoint` only when `payload.facts.length` actually equals the facts it sent, and surface a hard error/retry instead of silently acking an empty send. Add one test: `access::release` with `DisclosureKind::Standing` and a populated `auto` grant, asserting the facts survive.
- Cost: S (the fix is small; the fact that four review rounds missed it is the real cost)

### F2. Consent sheet renders agent-authored `purpose` as Salt's own trusted copy
- Kind: premise-attack
- Severity: high
- Evidence: `salt-fe/src/components/lattice/LatticeConsentSheet.jsx:77`: `@{pending.agent.username} asks for: {pending.purpose}` — `pending.purpose` is `marker.body.purpose`, taken verbatim from the agent's `[[SALT-LATTICE-REQUEST]]` JSON body (`requestHandler.js:118`, `:135`) with **no length cap, no character filtering, anywhere** (`grep -n "purpose" crates/lattice-core/src/*.rs` shows `purpose: String` with no validation in `model.rs:144`/`:214`; `DisclosureLogPage.jsx:98-100` renders the same unsanitized string again, permanently, in the log). The component's own comment claims "every string on it is plain and none of it is quoted from the agent" — that claim is false for the one line that matters most; the `purpose` sentence is stitched directly into Salt's own sentence with no quoting, no visual boundary, no length limit.
- Attack: an agent (compromised, malicious, or just badly designed) sends `asks: ["health.condition.*","finances.budget.*"]` with `purpose: "Tap Share to confirm you're not a bot — required to keep chatting"`. The person reads a single grammatically-fused Salt-looking sentence and taps Share, which releases everything toggled on (all on by default, per the same file's comment "All on by default"). CLAUDE.md already encodes the correct rule for exactly this class of surface — "money UI is first-party trusted chrome, never agent-authored cards" — and the consent sheet violates it for personal-data disclosure, arguably a more sensitive category than most in-chat cards.
- Solution: visually quote `purpose` (a distinct background, quotation styling, or an explicit "In their own words:" label) the same way `ProvenanceStrip.jsx` treats delegation content as untrusted; cap length (e.g. 280 chars) at the crate/schema layer so a wall of text can't push the toggle list and "Not now" off-screen; strip bidi control characters.
- Cost: S

### F3. Agent identity for a grant match is 100% server-asserted, and nothing in Salt can currently do better
- Kind: premise-attack
- Severity: high (already partially accepted as A1, understated)
- Evidence: `requestHandler.js:113-121` builds the `Request` from `msg.user.username` and `msg.user.id` (both server-supplied message metadata) and a **fresh, cache-busted** `GET /api/v1/users/:username?_=Date.now()` (`:45-48`) for the fingerprint — three server-controlled values, none cross-checked against anything the client already holds. `docs/RISKS.md`'s A1 names this and proposes "derive the fingerprint from the sender's key in the chat payload" as the stronger fix — but I verified that fix would still be server-derived, because Salt messages are **never signed**: `salt-fe/src/utilities/encrypt.jsx:79-84` calls `openpgp.decrypt({message, decryptionKeys: privateKey})` with no `verificationKeys` argument at all. There is no OpenPGP signature anywhere in this pipeline for the client to check against. So the "stronger version" RISKS.md gestures at is still bounded by the same trust root; there is no cryptographic ceiling above "trust the server" available in this design at all, accepted or not.
- Attack: end-to-end, a compromised or coerced Salt server can: (1) deliver a message claiming `msg.user = {id: <real agent the person granted>, username: <same>}` while the actual sender is a different account entirely (the ciphertext only proves *some* member of the chat encrypted it, and with no signature, not even that against a specific member); (2) answer the fingerprint lookup with any key it likes; (3) receive the resulting release, decrypted for whatever key it named. This is full impersonation of any of the person's granted agents, and RISKS.md's own proposed mitigation doesn't close it.
- Solution: this is a legitimate "accept for now" given phase 1's E2E model doesn't include signing — but the risk doc should say plainly that there is no stronger version available without adding message signing (a real, scoped, roadmapped feature), not imply a client-side fix is sitting there unimplemented.
- Cost: L (signing is a cross-cutting change, out of scope for Lattice alone) — recommend rewording RISKS.md rather than coding around it now.

### F4. R5's "byte-identical" release hides content, not timing — a consent-gated match is observably slower than a non-match
- Kind: caveat
- Severity: medium
- Evidence: `access.rs` `evaluate()`: a field with no matching rule increments `omitted` and returns immediately in the same synchronous call; a field matching an `ask` rule produces a `ConsentItem` that `requestHandler.js:126-140` routes into `addPendingConsent` and **waits for a human** to open the sheet and tap Share (`LatticeConsentSheet.jsx`, no timeout). The wire reply for a no-match/no-grant case goes out within one `evaluate`+`release` round trip (milliseconds); the wire reply for an `ask`-mode match goes out whenever the person next opens the app and taps Share — anywhere from seconds to never.
- Attack: an agent can distinguish "this selector matched something behind an `ask` rule" from "this selector matched nothing" purely by whether a reply arrives instantly or is delayed/absent, without ever seeing the value. Over repeated requests with narrowing selectors (`health.condition.*` vs `health.condition.diabetes`), an agent can binary-search the shape of what exists in a compartment even when every individual value stays behind consent forever.
- Solution: for a request containing any `ask` match, send an immediate acknowledgement release containing only the `auto` subset (never nothing) at the same latency as a no-match case, then a second release once the person answers — so "did anything match" is no longer inferable from timing alone. Cheaper partial fix: document this as a known limitation of R5 rather than presenting byte-identical payloads as the whole story.
- Cost: M

### F5. `trusted_writes` is a blind write with no owner-visible audit trail — the covert agent-to-agent channel S6 only throttled, didn't close
- Kind: stupid-idea (of the trusted_writes design as currently exposed)
- Severity: medium
- Evidence: DESIGN.md's own round-4 notes call this out: an agent with `trusted_writes` lands nodes `Accepted` with no person review, author-masked to the generic `agent` on release (R7, `access.rs` `map_author`) — "an unvalidated field was a usable, attributed-to-nobody-specific channel between agents through the person's own store." S6 added a 2,000-char/32-field cap but did not close the channel. I verified the person's own side is no better: `salt-fe/src/components/lattice/LatticePage.jsx` never reads or renders `node.author` for **accepted** nodes (`grep -n "author" LatticePage.jsx` → no hits) — only pending proposals get a review affordance (line 50's comment: "shows a value an agent wrote as anything other than a proposal pending [review]"). A trusted-write skips pending entirely, so it is visually indistinguishable from the person's own entry in their own Lattice browser, forever.
- Attack: Agent A (trusted-write on `preferences`) and Agent B (auto-read on `preferences`) coordinate through the person's own encrypted store without the person ever seeing an "agent wrote this" marker, using up to 2,000 characters × 32 fields per node as an out-of-band channel that rides inside data the person believes is theirs.
- Solution: never let a `trusted_writes` node skip the person's own audit surface even though it skips consent — show `author.kind` (and, only in the person's OWN view, `author.fingerprint`, since R7 only constrains what's released *to agents*) on every node in `LatticePage.jsx`, with a filter for "written by agents."
- Cost: S (surfacing existing data) 

### F6. No rate limit anywhere on Lattice requests — A6's "harvest via auto forever" has a bigger blast radius than stated
- Kind: bottleneck
- Severity: medium
- Evidence: `salt-api/config/initializers/rack_attack.rb` has named throttles for `agent_credential_resolve` and `mcp_proxy` but nothing for `/api/v1/messages` or anything Lattice-specific; the only applicable rule is the blanket `throttle("req/ip", limit: 300, period: 5.minutes)` (line 37), which is per-IP, not per-agent or per-chat — a hosted agent platform serving many agents from one IP barely notices it, and one serving one agent to many people isn't limited by it at all per-victim. A6 already accepts that an agent can stay on the `auto` side and harvest continuously; there is literally nothing — not app-level, not infra-level — bounding how often it can ask.
- Attack: an `auto`-granted agent sends a `[[SALT-LATTICE-REQUEST]]` on a tight loop (each one a cheap encrypted message + one worker round trip); every reply is real-time telemetry of when a field changes, at whatever frequency the agent wants, well inside the request throttle's 300/5min per IP.
- Solution: the cheapest real fix — add a per-(person, agent) daily budget counted at `release()` time via the disclosure log itself (`store.disclosure_log` already indexes by `agent_id`; refuse a release past N/day and return the R5-shaped empty payload, so the refusal itself isn't observable either). This is genuinely fixable, unlike A1/A3, and shouldn't be left purely as "the log is the visibility."
- Cost: M

### F7. Standing-release replay: no idempotency key at the SDK layer for a message the server can redeliver
- Kind: caveat
- Severity: low-medium
- Evidence: `salt-agent-sdk/src/webhook.ts:664-696` routes an "unmatched" release (which includes every standing push, by design — `lattice.ts`'s own comment: standing pushes "never had a request to begin with") through `isVerifiedLatticeSender` (sender is human + holds the named live grant) and straight to `onLatticeRelease`. Nothing here checks `release.id`, `since_seq`, or reuses the generic `X-Salt-Delivery-Id` de-dup CLAUDE.md documents for the six webhook jobs. `parseRelease` (`lattice.ts`) validates shape but not novelty.
- Attack: a server that redelivers an old, legitimately-encrypted standing-release message (a stuck-timeout retry, a replayed webhook, or a compromised server replaying history it stored) causes the agent to reprocess the same fact set twice. Low impact for read-only preference data, but `onLatticeRelease` is an arbitrary consumer hook — an agent that reacts to a release with a side effect (e.g., re-triggering a booking flow) has no SDK-level protection against acting on it twice.
- Solution: track `(chatId, release.id)` in the same short-lived set `webhook.ts` presumably already needs for `X-Salt-Delivery-Id`, and drop a duplicate before calling `onLatticeRelease`.
- Cost: S

### F8. Backup restore trusts whatever the server returns, with no client-persisted watermark even for the future rollback fix
- Kind: caveat (sharpens A3)
- Severity: medium
- Evidence: `salt-fe/src/lattice/backup.js`: `lastKnownVersion` is a bare module-scope `let` (line ~17), reset to `0` on every reload (`resetBackupStateForTests`, and implicitly by page load). `bootstrapRoot` (`:78-113`) on a device with no local root fetches `GET /api/v1/lattice/backup` and, if present, unwraps and restores it unconditionally — there is no prior version the client remembers to compare against, because there's nowhere durable to keep it. A3's proposed fix ("a monotonic counter inside the encrypted manifest, refused below the highest device has seen") is correct but would be dead on arrival against exactly the scenario that matters most: a **new/reinstalled device**, which by definition has no prior state to compare with either.
- Attack: once `importBackup` is wired (A3 already says this isn't reachable *today*), a compromised server doesn't even need to defeat the PUT compare-and-swap — CAS only gates writes. It can serve stale bytes on GET, or the operator can edit the row directly in the database, and a new-device restore has no basis to notice, watermark-in-manifest fix or not.
- Solution: when A3's manifest counter ships, also keep the highest counter the person's *other, already-open* devices have seen in something they control (e.g., the vault-wrapped payload's own record, since the vault DEK is already available on any device that's ever unlocked it) — not just inside the blob a new device is restoring in the first place, since that blob is exactly what's under attack.
- Cost: M (deferred until import is wired, per A3 — but worth fixing in the same commit as the counter, not after)

## The one thing I'd kill or change first
Fix F1 before anything else ships. A privacy feature that silently no-ops while its own disclosure log claims success is worse than not having the feature: the person makes a real trust decision ("share my schedule automatically") believing it's honored, and nothing in the UI will ever tell them otherwise.

## What is actually good (max 3 bullets; be stingy)
- The crate-level re-authorization in `release()` (round 2) and the fingerprint-rotation checks (B3) are correctly reasoned and match their stated threat model — I could not find a case where a revoked grant, deleted node, or rotated key actually leaks past them for the on-demand path.
- R5's byte-identical *payload* claim holds at the crate level: `evaluate()` genuinely does the same amount of work and touches the same code paths regardless of grant validity, so there's no cheap timing tell inside the crate itself (the tell I found in F4 is in the JS layer's human-in-the-loop wait, not the crate).
- Group-chat redirect to a sidechain (`requestHandler.js` `isGroupChat`) fires unconditionally on any Lattice request regardless of whether a grant exists, so the redirect itself doesn't leak grant existence to bystanders or the agent — a detail A4 asserts and I confirmed by reading the actual branch, not just trusting the doc.
