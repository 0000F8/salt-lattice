Lattice Under Attack

Six contrarian reviewers (architecture, security, implementation, cryptography, datastore, agentic) were told to assume Lattice is wrong until the code proved otherwise. They read the crate, the worker, the web-app glue, the API and the agent SDK on the lattice branches, and came back with 49 findings. This page is the synthesis: what would kill it, what each lens found, which accepted risks they dispute, where they disagree, the identity and many-devices questions the owner raised, and an ordered fix plan.

Verdict

Synthesised from six independent verdicts. Where they agreed, it is stated flatly.

The crate is the strongest part and the least important part. Every lens conceded that the Rust core's access rules hold under direct reading: deny by default, byte-identical denial, re-authorisation at release time, rotated-key refusal. Every lens also found that the decisions feeding that core are made in JavaScript glue with none of the crate's test discipline, and that is where three of the eleven criticals live.

Two of the criticals are not attacks, they are the product not working. Standing pushes deliver zero facts while logging success and acknowledging the checkpoint. And there is no way for a person to type a fact into their own Lattice: the only writers are agents proposing what they already know and an on-device model measured at 2.9% recall. The consent machinery currently guards an empty graph.

The single-device assumption was never designed, only assumed. Two tabs or two devices compute the same next sequence number and one silently drops the other's writes. The backup restores the key but not the data. Storage eviction has no recovery state. "The person's phone" is a mental model, not an invariant.

Destroy does not destroy. Compartment keys are derived, so deleting a file leaves a key that still opens any older backup. Compaction cannot be reached from JavaScript at all, so every file grows forever, and the only performance number was measured against a one-frame file that production can never produce.

Eight that would kill it

The criticals, merged across lenses where two reviewers hit the same thing. "Confirmed" means the lead re-read the code and reproduced the reasoning; "reviewer-cited" means the reviewer's file and line references stand on their own.

  1. K1Standing pushes deliver nothing and log successcriticalconfirmed

    evaluate gates every field on the request's asks. The disclosure log shows an entry with no fields. No test exercises the standing kind of release.

    Fix: a standing-aware path in release that re-checks against the grant's auto selectors instead of the request's asks, plus one test with DisclosureKind::Standing. Ack only when the sent facts match. Cost S

  2. K2Nothing fills the graphcriticalconfirmed

An agent can only propose what it already knows, which is the thing the grant flow exists to avoid needing. A new account's Lattice stays empty, so every guarantee below protects nothing.

  3. K3Two tabs silently drop each other's writescriticalreviewer-cited

    Each worker derives next_seq from what it loaded. Two sessions open on the same files compute the same number, both append a record at that seq, and on the next open apply_record treats the second as already applied and discards it. No locks, no broadcast channel, no mention of tabs anywhere in the docs. The first write from each session collides, deterministically.

    Fix: a Web Locks lock per compartment before any flush; a second context refuses open or downgrades to read-only. A merge protocol is out of scope, detect-and-refuse is not. Cost M

    implementation F1 · store.rs:159-166, 237-240 · lattice.worker.js:201-221

  4. K4Destroy does not destroy the keycriticalreviewer-cited

    A compartment key is a pure function of the root key and the compartment name. Destroying deletes the file and writes a marker, and the marker lives in the current device's system compartment. Any older backup blob still decrypts under the same derived key, and importBackup writes the old ciphertext straight back with no destroyed check. A person's explicit destroy is reversible forever by anyone holding an old blob, the server included.

    Fix: a random key per compartment, wrapped by today's derived key; destroy deletes the wrap. Already named as the phase 2 option; it stops being optional once backup rows exist, which is at first use. Cost M

    cryptography F1 · crypto.js:135-137 · lattice.worker.js:574-590, 615-644

  5. K5Compaction is unreachable and the perf gate measured a file that cannot existcriticalconfirmed

    Store::compact exists in Rust and is bound to nothing: not on the wasm class, not in the worker, not in the op dispatcher. Every write, accept, checkpoint and log entry appends a frame forever. The 5,000-node gate was built by one batched call, producing one frame per compartment; real use flushes after every call, producing thousands of frames each needing its own OPFS read and WebCrypto decrypt. The wall-clock number that would show this is recorded but never gated.

    Fix: bind compact, run it past a frame-count threshold (after K3, since a whole-file rewrite with a second tab open is the worst case). Rebuild the fixture from thousands of single writes and gate wallMs. Cost S + M

    datastore F1, F2 · implementation F5 · architecture F2 · lattice-wasm lib.rs:86-158 · fixtures.rs:44-68 · perf.spec.js:37

  6. K6Trusted writes and delegation both bypass the whole pipelinecriticalreviewer-cited

    An agent with trusted_writes on a compartment lands facts as accepted with no review, up to 2,000 characters of free text per field. A different agent with an auto grant on that compartment later receives that text masked as author: agent, indistinguishable from any other fact, and reads it into its model context as the person's own data. Separately, an agent that legitimately received a fact can paste it into a free-text delegate_to_agent task to an agent with no grant at all: no consent, no log entry, no revocation. The grant system governs the first hop only.

    Fix: trust is per writer, not per fact: a trusted-write node stays ineligible for release to any grant but the writer's own until reviewed once. Show author.kind on every node. Scan delegation tasks for values received via request_personal_data in the same process and refuse or at least log a forwarded event. Cost M

    agentic F2, F3 · security F5 · store.rs:342-359 · actions.ts:266, 321 · PersonalDataCard.jsx:155-165

  7. K7A request that arrives before the store is open is dropped forevercriticalreviewer-cited

    The incoming-message subscription is gated on "logged in", not on "Lattice ready". A request landing during reconnect, before the vault unlocks and open resolves, throws not_open, is logged to the console and never replayed. The SDK meanwhile tells the agent "you'll get a message when they next open Salt", a promise this path cannot keep. One arriving after open but before grant sync gets the byte-identical deny, which the person cannot tell from a revoked grant.

    Fix: buffer inbound Lattice markers while status !== "ready" and replay them keyed by message id once bootstrap finishes. Cost S

    agentic F1 · implementation F4 · LatticeRequestHandler.jsx:41-127 · lattice.worker.js:61, 101 · actions.ts:374-380

  8. K8Grant sync races itself and swallows the failurecriticalreviewer-cited

    syncGrants fires every agent's set_grant through Promise.all. All touch the system compartment; the worker's message handler is async and unserialised; each flush opens an exclusive OPFS sync access handle. With two or more grants the second flush throws, restoreFrame correctly re-queues the bytes, and then the caller catches the rejection with a bare empty handler. The grant sits unflushed until some unrelated call happens to touch the compartment. Nobody sees anything. And close on logout frees the store without flushing first, so re-queued data can be lost outright.

    Fix: a sequential loop instead of Promise.all; surface flush_failed; make close await a best-effort flush and guard restoreFrame against a freed store. Cost S

    implementation F2, F3 · sync.js:36-54 · lattice.worker.js:273-301, 499-507, 716-724 · client.js:76-93

Identity is not one thing

Raised by the owner mid-review. Checked against the schema, the access rules and the grant picker.

A person is several people: the one their employer's scheduling agent meets, the one a dating app's agent meets, the one their partner's agent meets. Lattice has one axis, the topic (identity, health, preferences…), and no axis for the audience. There is no field, type, rule or grant shape that says "this fact exists, and this class of agent must never learn it". The words sexuality, orientation, religion, politics, gender, audience, persona and sensitive appear nowhere in the schema, the design or the access code.

That produces three concrete leaks, none of which need an attacker.

  • The picker grants by topic, and topics are wide. The Personal data card offers preferences.* and preferences.food.*, never a field. A restaurant agent granted preferences.* on auto receives every fact anyone ever filed under preferences, including whatever Ion or a partner's agent proposed there about intimacy, and receives it in a standing push the moment it changes.
  • What has no type does not get refused, it gets smuggled. The closed schema has no place for a kink, an orientation or a faith, so an extractor puts it where it fits: a note on preferences.*, a relationships.person.detail value, a health.condition. Free-text fields are the least governed thing in the store and they are released under any selector that matches the parent type.
  • The root node is one self. identity.person carries one name and one pronouns field. Released under identity.* to any agent, it can out someone to an audience they present differently to. There is no "as strangers know me" and "as friends know me".

What to change

  • A tier on every fact (public, contacts, private, never), stored on the node, defaulting from the compartment and from the provenance of the chat it was extracted from. Ion and agent proposals carry the tier of their source chat; a fact from a lane with someone marked partner defaults to private.
  • A ceiling on every grant, defaulting to public for an agent the person has never dealt with, which the crate enforces inside evaluate beside the selector match so the guarantee is a rule with a test, not glue.
  • Sensitive compartments that cannot be auto. Sexuality and intimacy, religion, politics, immigration status, mental health: their own compartments, ask-only, excluded from standing pushes, excluded from the compartment-level checkbox so a wide grant can never include them by accident.
  • Free text takes the strictest tier of its node's compartment, because a note is where anything without a type ends up.
  • More than one self. identity.person gains per-tier presentation: the name and pronouns a stranger's agent gets can differ from what a friend's agent gets. A persona is a named ceiling, so "grant this agent as Work" is one tap that means public plus the work compartment.
  • Provenance on facts, not just authorship. R7 masks who wrote a fact; nothing records what kind of room it was learned in. Keep the mask on release, keep the origin on the node, and let the tier default follow it.

The cost is one column on the node, one field on the grant, one check in the crate and a picker that shows tiers. Without it the privacy story is "we cannot read your facts, but any agent you let near a topic can", which is not the story the product tells.

Many devices

Owner: "I have a browser, an iPhone and an iPad on the same account. Is this solved at the Salt level?" Checked against the API, the web app and the Lattice worker.

For everything except Lattice, yes, and by one pattern. The server stores only ciphertext and every device derives the same keys from the login password. The PGP private key sits on the server encrypted under the messages key, so a new device unwraps it after sign-in. Every chat message is encrypted for every member, the sender included, so a new device reads the whole history. Wallet secrets are the same shape. Realtime goes to one Action Cable stream per user, so every connected device hears every event. Push subscriptions are per device. Nothing a device needs is only on that device.

Lattice breaks the pattern in three places. The files are in the browser's private file system, the root key is in that browser's IndexedDB, and the sequence counter is derived from whatever that browser loaded. The backup row restores the key but not the data. So a second device opens an empty graph, two devices collide on the first write, and an evicted cache is indistinguishable from an empty account. One more thing this question exposes that no lens caught: an agent's request reaches every open device at once through the cable, so today every device would evaluate it, every device would show the consent sheet, and every device would send its own release.

On iOS, Safari and the home-screen app keep separate storage, so "my iPhone" is already two devices for anything kept on the device.

The fix: put Lattice's log where Salt already solves this

Salt is an end-to-end encrypted, server-sequenced, append-only log delivery system. That is what a chat is. Lattice's store is an append-only log of encrypted frames. Stop keeping it on the device and send the frames through the same machinery messages use: the server stores and orders ciphertext it cannot read, every device pulls, the device's files become a cache.

What changes, by layer

  • API, small. A lattice_frames table (user, server-assigned per-user seq, compartment, device id, ciphertext blob). POST /api/v1/lattice/frames assigns the seq and broadcasts a content-free lattice_frame event on the user's cable stream. GET /api/v1/lattice/frames?since= returns frames in order. A compact call accepts a snapshot frame for a compartment and drops that compartment's earlier frames, which the server can do without reading any of them. The backup row keeps only key_wrap. This is the messages pattern with the chat removed.
  • Crate, medium. Records get a ULID identity instead of a local counter, and order comes from the server seq of the frame that carried them. The store already sorts and rebuilds its index at open; a pull does the same. A local write applies optimistically and is re-sorted when its frame's seq arrives. next_seq goes away, and with it the collision.
  • Worker, medium. Durability moves from "on disk" to "acknowledged by the server". OPFS becomes a cache written lazily, which also removes the exclusive-handle race from grant sync. Open is: load the cache, pull since last_seq, then ready. The resume signal that already re-fetches chats triggers a pull.
  • Web app, small. No new pages. The "not restored yet" state disappears because there is nothing to restore; an evicted cache is a slower open, not an empty account.
  • Requests on several devices. The reply is a chat message, so every device sees the release arrive and dismisses its own consent sheet. For auto releases, a content-free claim endpoint (POST /api/v1/lattice/claims with a hash of the request id, first caller wins) elects one device to answer. Standing pushes already write a checkpoint record; with checkpoints synced, a device pulls before it pushes and only pushes above the highest checkpoint it has seen, and the SDK's release-id dedup catches the rare overlap.

What it costs in trust, honestly

  • The server learns nothing new in kind. It already holds the whole blob, the key wrap and every message. It now holds the same bytes as many frames, and it sees when each compartment was written, which is the same class of metadata it has for chats. Pad frames to size buckets so it cannot count facts.
  • The server becomes the sequencer. That is already true for messages: it can withhold or delay, it cannot forge, because a frame is authenticated under a key it does not have. A device whose last_seq is above what the server returns detects a rollback; a wiped device still cannot. That is the accepted risk from A3, now stated for what it is.
  • Destroy still needs per-compartment keys (K4). Server-side frames make an old blob more available, not less, so the key wrap must be the thing that dies.

What it retires from this review

K3 (sequence collision), A3 (second device empty), A7 (eviction), most of K5 (compaction via snapshot frames), and the exclusive-handle half of K8. It does not touch K1, K2, K6, K7, identity tiers, or the crypto integrity findings. The rejected alternatives: frames as messages to yourself (works, reuses everything, pollutes the chat list and the messages table), a CRDT (every write is already a version, so there is nothing to merge), and keeping the device primary with a three-way backup merge (needs vector clocks and still has no live sync).

Disputed accepted risks

docs/RISKS.md accepts six items from the earlier review. Four of them drew objections.

A1
Understated. The doc offers a "stronger version" (derive the fingerprint from the sender's key in the chat payload). Security verified Salt never signs messages and the chat payload's keys also come from the server, so no stronger client-side fix exists without message signing. Say so plainly rather than implying one is waiting to be implemented.
A3
The proposed fix does not cover the case backups exist for. A manifest counter refused "below the highest the device has seen" refuses nothing on a wiped or new phone. Close the common case (a live device un-destroying a compartment) with a tombstone list in the encrypted manifest, and write down that first-restore-onto-a-wiped-device has no rollback defence in this architecture.
A5
Not one dead rule, a structural inversion. Every security-relevant classification (channel, identity, key freshness) is resolved once in plain JS and handed to Rust as ground truth. The 42-test suite proves properties of a model whose inputs are the least-tested code in the stack.
A6
Accepted without a bound. Continuous auto harvesting is accepted, but nothing limits its frequency at all, and the consent UX predicts everyone converging to auto. A per-agent daily budget at release time, refused with the R5-shaped empty payload, is the cheap version.
A2, A4
Stand as written. Security confirmed the group-chat redirect fires regardless of grant existence, so bystanders learn nothing about grants; cryptography confirmed the raw root bytes never reach redux, a log or an action.

Where they disagree

Six reviewers, six different first moves. That spread is itself a finding: the problems are not in one place.

  • architectureShip manual fact entryEvery dollar of crate rigor protects a hypothetical until a person can type a fact in.
  • securityFix the standing no-opA privacy feature that silently does nothing while its log claims success is worse than not having it.
  • implementationWeb Locks before anything shipsThe only finding that deletes a person's own data with no trace, on the one scenario the product calls routine.
  • cryptographyPer-compartment random keysEvery other crypto finding is a variant of "an old copy comes back"; this is where it reverses an explicit destroy.
  • datastoreKill the fixture, keep the budgetNobody has a number for when growth stops being tolerable, because the only number measures a shape that will never exist.
  • agenticClose the trusted-writes bypassThe one hole that works exactly as designed rather than needing a compromised server or device.

Two direct contradictions

  • Sender key from the chat payload. Cryptography proposes it as a cheap upgrade to the fingerprint check. Security points out the chat payload's public keys are also server-supplied and nothing is signed, so it removes a round trip and no trust. Security is right; keep the change for the round trip, not the guarantee.
  • Was wasm the wrong call? Architecture says plain JS over IndexedDB would clear every gate with a fraction of the toolchain. Datastore says SQLite in wasm would fix indexing and compaction for free but at three to six times the download, past the size gate. Both are true; the honest framing is that the 300 KB gate, not performance, is the argument for this crate.

What survived six attacks

  • Release re-derives authorisation from a fresh evaluate instead of trusting its facts argument. Named by four of six lenses as the one pattern most consent systems get wrong and this one gets right.
  • takeFrame and restoreFrame treat "encrypted but not yet durable" as distinct from "lost", and chose the race-free design over an ack watermark.
  • The primitives. A real CSPRNG root, HKDF, AES-256-GCM, non-extractable keys, and the padded, separately keyed backup manifest. The padding just was not applied to the one payload that needed it.

Is this the right shape?

Owner: "I need Salt to be the place where agent execution and interaction get trusted, because the source of information about the user's identity and preferences is bastioned there. That is the user's authority, and thus Salt's authority."

The vision is right and Salt already owns the hard half. Authority means something a third party can verify. Salt registers the person's keys, knows their standing (verified contacts, account age, real-money history, trust score, work and hiring records), holds agents' third-party credentials and lends them under grants, and runs the rails where consequences land: transfers, invoices, work orders, spending policies. A counterparty can check all of that against Salt. Lattice adds the other half, the person's own facts, and holding them on the device is the right call given the promise that Salt cannot read them.

The unit of release is the wrong shape. Lattice releases an unsigned prose fact, inside a chat, only while the phone is awake, with no id and no audience. Only the receiving agent can know it came from the person under a grant. Salt's authority has nothing to sign, and the worst findings above follow from that directly: facts launder into delegation prose (K6), duplicate because they cannot be referenced (G4), and drop when the phone is asleep (K7). An authority that is offline while the person sleeps is not one agents can execute against.

Ion: the wrong first bet, not the wrong idea

The bastion has to be full and current without a third party reading the chats. Open extraction at 2.9% recall will not do that for a long time. Three cheaper fillers come first: the person typing a fact (K2), capturing a fact at the moment the person answers an agent's question in chat (the answer is the fact, and it is already typed), and the embedding recall that works today. Extraction is the optimisation once the owner's own labelled conversations exist, which is the decision already recorded in salt-ion's baseline.

The reframe in one line

Salt is the authority for identity, standing and consequences. The person is the authority for facts, held on their device. Both issue verifiable claims under one Salt-registered key, and agents execute against claims, not against chat. Lattice is the right store for that. Its wire protocol, the fact in a message, is the part to replace, and it is the same change that fixes the review's structural findings.

Cost, honestly: signing needs the person's private key on the device, which the vault already provides, and a verifier path that fetches keys from Salt, which exists. Salt does not sign messages today (S3), so this is the first signed artefact in the product and the release format, the SDK's receive path and the disclosure log all change. Medium to large, and it is the change that makes the other twenty-four worth doing.
