# Agentic review

## Verdict (3 sentences, contrarian, honest)
Lattice is engineered like a security product but deployed like a chat feature, and the two personas it actually serves — the person and the agent developer — get the worse half of that trade: the person gets an empty graph and an all-or-nothing consent sheet, and the agent developer gets a protocol that can silently swallow a request forever and a `Fact` shape too thin to ever correct itself. The two structural bypasses (`trusted_writes` skipping human review entirely, and free-text delegation laundering a released fact to an ungranted agent) are worse than anything on the accepted-risk list in `RISKS.md`, because they don't require a compromised server (A1) or a compromised device (A2) — they work exactly as designed, today, on the honest path. Ion's 2.9% recall means none of this matters yet for most people: the feature this whole stack defends is, on current numbers, going to be empty.

## Findings

### F1. A request arriving before the vault unlocks is answered by an exception, then never again
- Kind: bottleneck
- Severity: critical
- Evidence: `salt-lattice/web/lattice.worker.js:61,101` throw `{code:"not_open", message:"call open() before using the lattice"}`; `salt-fe/src/lattice/client.js` `call()` is a bare `send("call",...)` with no auto-open; `salt-fe/src/lattice/backup.js:101-104` returns `{pending:true}` and sets status `"locked"` when `!canWrapBackup()`; `LatticeRequestHandler.jsx:109-127` subscribes to incoming messages in an effect gated only on `active` (logged in, not an agent) — not on `status === "ready"` — and its only failure handling is `.catch(err) => console.error(...)`.
- Attack: an agent's `[[SALT-LATTICE-REQUEST]]` lands the instant the person's tab reconnects, before the second bootstrap effect has unlocked the vault and called `open()`. `handleLatticeRequest` calls `evaluate` on an unopened store, the worker throws `not_open`, the error is logged to the console and dropped. Nothing re-delivers that specific message once the vault does unlock — there is no replay queue, only the live subscription that already fired once. The agent's `request_personal_data` tool times out at 15s and reports `"pending"` with the promise "you'll get a message when they next open Salt" (`actions.ts:374-380`) — a promise this code path cannot keep, because the person's phone genuinely never saw the request.
- Solution: buffer inbound Lattice markers that arrive while `status !== "ready"` and replay them once `runBootstrap` finishes, keyed by message id (dedup against `alreadyProcessed`-style tracking already used elsewhere in the stack).
- Cost: S

### F2. Delegation is a plaintext bypass of the entire grant → consent → disclosure pipeline
- Kind: premise-attack
- Severity: critical
- Evidence: `salt-agent-sdk/src/actions.ts:266` — `delegate_to_agent`'s `task` is free text (`const marked = delegations.wrap(ctx.depth + 1, task)`), and it goes straight into a 1:1 with the target agent; `requestPersonalData` (`actions.ts:321`) explicitly excludes observers from who can be *asked*, but nothing stops the delegating agent from *telling* facts it already legitimately holds.
- Attack: agent A holds a real grant and legitimately releases the person's peanut allergy and cuisine preference via `request_personal_data`. A then calls `delegate_to_agent` to a restaurant-recommendation agent B with `task: "find dinner options, they're allergic to peanuts and like Japanese food"`. B has no Lattice grant at all, yet now has the fact, permanently, in its own conversation history — no consent sheet, no `DisclosureEntry`, no selector, no revocation surface. The whole apparatus in `access.rs` (deny-by-default, R5, R9, disclosure log R12) governs the *first* hop only; every subsequent hop is ordinary prose. The person's own root-observer membership on the A↔B chat (`chats_controller.rb:754`, muted, zero-unread) is the only chance they'd ever notice, and nothing surfaces it as a Lattice event.
- Solution: the `Fact` value it received from a grant this session should carry a non-forwardable marker the SDK enforces client-side — `delegate_to_agent`'s `task` string gets scanned for values matching facts obtained via `request_personal_data` in the same process and refused (or requires the delegate to hold its own equivalent grant, checked server-side before the message sends). Cheap partial fix: log a `lattice_fact_forwarded` event when a delegation's task text contains a released value, so it's at least visible to the owner.
- Cost: M

### F3. `trusted_writes` lets an agent write attacker-controlled text with zero human review, which a *different* agent can later receive as trustworthy "person" data
- Kind: stupid-idea
- Severity: critical
- Evidence: `crates/lattice-core/src/store.rs:342-359` — `initial_status`: `AuthorKind::Agent` whose fingerprint resolves to a grant with the compartment in `trusted_writes` gets `Status::Accepted` immediately, never `Pending`. `PersonalDataCard.jsx:155-165` exposes this as one checkbox per compartment, "Let it write directly here, instead of proposing," with no further explanation of what "directly" means. Field values allow up to `MAX_TEXT_LEN` = 2,000 chars (`DESIGN.md` round-4 S6) of free text in `note`.
- Attack: person grants agent X trusted writes on `preferences`. X (compromised, or simply badly aligned) calls `propose_personal_fact` with `note: "<2000 chars of injected instructions>"` on a real type. It lands `Accepted`, no review, ever. Weeks later agent Y — a completely different, unrelated agent — has an `auto` grant on `preferences.*` and calls `request_personal_data`; the poisoned note comes back masked only as `"author":"agent"` (R7), indistinguishable from any other fact, and lands in Y's model context as "the person's own data." `salt-claude-agent/src/index.js:159-186` frames its own releases as `[system -- not a chat message]... treat exactly like a tool result`, which is good host-side hygiene, but that discipline lives in one reference implementation, not in the protocol or the crate — `salt-app-example`'s pattern gives no such guarantee.
- Attack, secondary vector: the same free-text `purpose` field an agent puts on a *request* is rendered verbatim to the person on `LatticeConsentSheet.jsx:77` (`"@{username} asks for: {purpose}"`) with zero framing distinguishing it from Salt's own copy — a request whose stated purpose is a lie ("to verify your account, share your phone number") is a plain social-engineering vector the sheet does nothing to blunt.
- Solution: trusted-write nodes should still require the FIRST review before ever becoming eligible for release to a grant other than the writer's own (i.e., trust is per-writer, not transitively per-fact); cap `note` length much lower for agent-authored content specifically, and prefix the consent sheet's purpose line with fixed chrome ("An agent is asking. Its stated reason:") to visually separate agent prose from Salt's own text.
- Cost: M

### F4. `Fact` has no id, so an agent can never correct or supersede what it previously learned — only pile up duplicates
- Kind: caveat
- Severity: high
- Evidence: `PROTOCOL.md:25` — the released `Fact` shape is `{path, type, field, value, author, updated}`, no `id`; `salt-lattice/docs/DESIGN.md` "Decided while building" notes `Fact.path` is derived from the type's dotted segments plus the node's `name`, "not a raw node id." `propose_personal_fact`'s schema (`actions.ts` tool def) takes only `{type, parent_name?, fields}` — there is no `fact_id`/`node_id` parameter anywhere an agent could reference to edit.
- Attack: the person tells agent Z their allergy severity changed from mild to severe. Z's only tool is `propose_personal_fact`, which can only create a brand-new pending node — it cannot reference, update, or supersede the existing `health.allergy` node, because it never received that node's real id (only a human-readable `path`, and paths collide whenever two nodes of the same type share a `name`, e.g. two house moves both named "Home"). The person now has two allergy entries and must manually notice and reconcile them in the Proposals review; if they accept both, `evaluate` for a future request has no rule for picking the current one — it releases whichever the query returns, silently.
- Solution: include the real node id in every consent-approved `Fact.path` reply to an agent that already holds `trusted_writes` or has previously proposed that exact node (a scoped id, not the raw ULID given to every requester) so a genuine update tool can target it; add a `supersedes` field to `propose_personal_fact`.
- Cost: M

### F5. The closed schema refuses exactly the fields real agent tasks need, so the workaround is asking in plain chat anyway
- Kind: premise-attack
- Severity: high
- Evidence: `salt-lattice/docs/DESIGN.md:55-56` (R14): "There is deliberately no type for a private key, seed phrase, password, account number or card." No schema-extension mechanism exists (`R1`, closed schema, `schema.rs`).
- Attack: a travel-booking agent needs a passport number or a frequent-flyer number to actually book anything. Lattice refuses by design; `request_personal_data`'s `asks` can't name a nonexistent selector meaningfully (silently absent). The agent's only path forward is to ask in the ordinary chat, in plaintext, over the exact protocol Lattice exists to replace — the feature's own security model degrades to zero for the highest-value use cases, and the person has no way to tell, from inside the flow, that this particular ask fell outside Lattice's protection when a nearly identical-looking one (home address) did not.
- Solution: accept, because widening the schema to cover identity documents is a real scope decision the owner should make deliberately (R1 exists for good reasons — no free-form types). But the UI should say so: when an agent's `asks` includes a selector the schema has no type for, or when the agent is chatting about something schema-shaped-but-refused, the person should see a passive one-line note ("This can't go through your private data — it'll be an ordinary message") rather than nothing.
- Cost: S (for the UI note); L (if the schema is actually widened)

### F6. All-or-nothing consent on mixed requests, plus a grant an agent can read itself, predicts convergence to blanket Auto
- Kind: bottleneck
- Severity: medium
- Evidence: `salt-fe/src/lattice/requestHandler.js:98-101` — "any `ask` item holds the WHOLE request for the person's consent... rather than half-answering it now and half later"; `PersonalDataCard.jsx`'s `GrantEditor` (`toggleSelector`, line ~71) defaults every newly-checked selector to `"ask"`, with a plain two-state dropdown (Auto/Ask) and no visibility into how often a given selector actually gets asked; `RISKS.md` A6 already names the underlying dynamic ("an agent can ask only for auto selectors, never trigger a consent sheet, and harvest continuously, with the disclosure log as the person's only visibility").
- Attack: a person grants an agent five selectors, one on `ask` because it feels sensitive. Every single request that touches any of the other four now also stops the conversation for a full consent sheet, because the batch is all-or-nothing. After the third interruption for what "feels" like a routine question, the rational move is to flip that one selector to Auto — there is no UI signal for "you're about to remove your only friction point," no per-selector ask-frequency shown, and the standing-push "Keep it current" toggle (`PersonalDataCard.jsx:172-181`) is presented as a single global switch per grant, not per selector.
- Solution: let auto items in a mixed request release immediately (already computed by `evaluate`) while only the `ask` remainder waits on the sheet, instead of holding the whole batch; show a lightweight per-selector "asked N times this month" stat on the grant row so the tradeoff is visible before someone flips it.
- Cost: M

### F7. There is no way to manually add a fact — the graph a grant protects is, for almost everyone, empty
- Kind: bottleneck
- Severity: high
- Evidence: two independently-shaped searches turned up nothing — `grep -rn "put_node" salt-fe/src/` matches only `requestHandler.js` (agent- and Ion-authored proposals) and its test file; a second search for `author.*you`/`kind: "you"` across `salt-fe/src/` matches nothing outside `theme.js`'s unrelated comment. `LatticePage.jsx` offers search, compartment counts, and Accept/Reject on pending proposals — no "add a fact" affordance anywhere. `salt-ion/docs/BASELINE.md`: untuned Qwen2.5-0.5B gets 2.9% exact recall / 63.2% schema-invalid; SmolLM2-360M gets 0.0% exact recall.
- Attack: a brand-new grant has nothing to release (`{auto:[], ask:[], omitted:5}` in practice), Ion cannot fill it at any usable rate, and the person has no first-party way to type in "I'm allergic to peanuts" themselves outside of hoping an agent proposes it correctly (unlikely, per baseline) and then accepting that proposal. The entire access-control apparatus this review is auditing has, on current numbers, nothing to protect for the median new user — which also means the UX of grants, consent sheets and disclosure logs is functionally untested against real usage until this changes.
- Solution: ship a minimal manual entry form on `LatticePage.jsx` gated by the same schema the picker already fetches (`GET /lattice/schema`) — it's a strict subset of `PersonalDataCard`'s type-browsing UI, reusing `humanizeSelector` and `COMPARTMENT_LABELS`. This is the highest-leverage, lowest-cost fix in this whole review.
- Cost: S

### F8. Standing pushes are a 90-day unattended channel with no live notification
- Kind: caveat
- Severity: medium
- Evidence: `PROTOCOL.md:34-42` — standing releases fire automatically on `auto` fields, diffed since last checkpoint, for up to 90 days; server-side notifications exist only for `lattice_standing_expiring`/`_expired` (`PROTOCOL.md:72-74`), never for a push itself, "since requests and releases are invisible to the server." `PersonalDataCard.jsx:172-181` discloses this honestly at grant time ("a copy stays with the agent, and revoking this can't take that copy back") but that's the only moment it's said.
- Attack: three months of a person's changing preferences flow to an agent with zero per-event visibility; the only place to check is the disclosure log page, which nothing prompts anyone to open, and Salt's own Activity feed convention (badges, toasts, `notifications_prompt_shown`) is not extended to Lattice at all.
- Solution: accept the *design* (server-blind is the whole privacy point) but add a client-local, non-server counter — a small "3 updates sent to @agent this week" line on the grant row in `PersonalDataCard`, computed from the worker's own disclosure log, no server round trip needed.
- Cost: S

## The one thing I'd kill or change first
Kill `trusted_writes`' immediate-accept path (F3) before shipping anything else — it's the one place the design lets an agent's raw text become "the person's own record" with no human in the loop at all, and it composes badly with F2 (that poisoned record can then travel to a completely unrelated agent under someone else's grant). Everything else in this review is a UX or availability problem; this one is a trust-boundary hole.

## What is actually good (max 3 bullets; be stingy)
- `R5`'s byte-identical no-match/no-grant/revoked release, and the round-2/round-4 re-validation of `release()` against a fresh `evaluate()` rather than trusting the caller's `facts` — closes the exact class of bug ("authorization decided once, in JS, then never rechecked") that sinks most consent systems.
- `webhook.ts`'s chat+sender binding on `register()`/`classifyRelease` correctly treats a request's plaintext id as public and non-authoritative, and separates "matched" from "refused" from "unmatched" so a forged release can't be silently accepted.
- The tool descriptions in `actions.ts` (`request_personal_data`, `propose_personal_fact`) are unusually disciplined about telling the model what NOT to assume ("NEVER invent... a fact you didn't actually receive"), and `salt-claude-agent`'s `onLatticeRelease` prompt explicitly frames released facts as data, not instruction.
